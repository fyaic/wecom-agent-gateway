本轮基于 `094be1c`，目标仍是 Kernel 无关、快速方便稳定的 IM 中间层。
三位子 Agent 分别实现授权维护入口、ACP 生命周期补强、升级/回退演练；主 Agent 集成、复查和验收。
没有发布新版本、重新注册 Bot、切换生产 Agent 或修改现有凭据。
Keeper 源码接口复核基线为本地 `b2a1edb`；包装器不将它复制或加入 Gateway 运行时依赖。

## 授权现场：不能复用错 Bot

9 月 14 日 session 记录了 SDK 私聊收发/主动推送成功、CLI 消息接口返回 `850003`。
当时记录不能证明所有办公能力都过期，也不能证明未来身份配置不变。

9 月 23 日重新使用 Gateway 配置的 CLI 目录检查：CLI 1.1.0，`auth show --status`
仍为 authorized；`identity whoami` 显示其属于**另一个业务 Bot**，而非 Gateway Bot；
该 CLI 的消息会话查询返回授权过期。现有 keeper 私有实测配置也不匹配 Gateway。
因此这次 CLI 失败不能归因到 Gateway Bot；不修改该账号、不复用其写探针。

真实执行 `pnpm auth:keeper` 并传入既有 keeper 配置，得到 `identity-mismatch`、非零退出，
在启动 keeper 前拒绝；没有变更授权。Gateway 的生产 CLI 工具开关原本关闭，未改变。
下一步必须先建立 Gateway 自己的同 Bot 配置与 CLI 身份证据，再做页面恢复和逐能力 API 复探。
当前包装器不自动导航、不安装周期任务，也没有真实 GUI 续期成功证据。

keeper 自身已有成功记录值得复用，但它不是官方续期 API，也不能外推为 Gateway 的验收。
尤其默认 `keepalive.py` 含文档写探针，不能作为无副作用的 Gateway 健康检查。
