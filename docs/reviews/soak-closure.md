# Linux soak 验收门复核

日期：2026-09-05。范围：已有 `scripts/linux-soak.ts`，不新增运行平台、后台任务或第二条 Bot 连接。
本次结论是**验收器的假通过缺陷已修复并有确定性回归**，不是 Linux 24 小时真实运行已通过。
目标依据：[产品基线](../product-intent.md)、[证据规范](../evidence-claims.md)。

## 发现与修复

| 原缺陷                                          | 可能产生的错误结论                                | 本轮修复 / 回归                                                                                                  |
| ----------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `/metrics` 失败或缺字段时 Outbox 缺省为 0       | 没有观测数据也显示已排空、无 dead                 | 五个状态必须齐全且为非负安全整数，拒绝重复/未知状态、负数、小数和 NaN；缺失值输出 `null`，门失败                 |
| 只检查起止墙钟，循环最后一次 sleep 后没有 probe | 两个相距 24h 的样本或末尾未采样时段被当成持续稳定 | 必须有完整窗口和截止时 probe；时间戳单调、首尾覆盖、采样空洞分别判定；假时钟的 24h 跳跃明确失败                  |
| PID、NRestarts、journal invocation 只记录不判定 | 进程已经崩溃重启却仍显示稳定通过                  | 验证 PID/InvocationID/计数有效；进程代际变化、restart 计数变化及 journal 多 invocation 均失败；报告不输出原始 ID |
| 健康端点只看 HTTP 200                           | `live:false` / `ready:false` 或无效正文可能算健康 | 要求 JSON 中对应字段严格为 `true`；重定向不跟随                                                                  |
| 只看最后一次 dead 数量                          | 运行中出现 dead 后被清理掩盖                      | 任一采样观察到 dead 都不能通过无死信门                                                                           |
| ready 故障时长按“失败样本数 × 间隔”估算         | 漏采/探针耗时使故障持续时间失真                   | 按观察到失败至恢复的时间戳计算，仍仅为采样证据，不声称连续精确测量                                               |

探针/调度开销容差是 `max(10s, requestTimeout)`，上限 30s；最大采样间隔为配置间隔加此容差。
默认 30s 采样对应最大 40s 空洞门。请求 timeout 超过 30s 会拒绝，不能靠调大 timeout 豁免长时缺采。
`systemctl` 和 `journalctl` 分别有 10s / 30s 超时；命令失败不产生通过结果。

## 输出与验收语义

- 报告升级为 **`schemaVersion: 2`**。Outbox final/peak 聚合可能为 `null`，表示不可验证，不能按 0 使用；
  新增 `sampling`、`metricsFailures` 和 `invocationChanges`。旧版本报告不能据此重新解释为已通过新门。
- `processStayedSame` 是**严格无重启稳定窗口**的门，不是“重启恢复能力失败”的结论。
  有计划的重启应单独保留操作、重新 ready、durable 恢复证据，然后开始新的稳定窗口；
  不把受控重启纳入此窗口后再偷偷忽略 PID 变化。
- `certifying` 表示选择了不少于 24h 的认证模式，必须同时检查 `passed` 与全部 `checks`；
  `--non-certifying` 测试即使通过也不能满足 24h 发布门。
- 正常默认门不允许 readiness 失败。`--expect-network-outage` 仅允许并要求观察 ready 下降/恢复，
  仍要求服务持续 live、最终 ready、排空、无 dead。`externallyAttested` 始终为 `false`。
- 有限采样不能排除更短暂的中断；健康与 Outbox 全零也不能证明这一天实际处理过用户消息。
  真实消息成功/失败/恢复矩阵必须另附，不由这个验收器制造。

## 本机只读环境检查

宿主系统是 macOS，未安装可直接使用的宿主 `systemctl`、Colima 或 Lima 命令。Docker Desktop 的
Linux daemon 可用，但当前容器列表中未发现本项目的 Linux/systemd 验收服务。
这只能证明有容器运行能力，**不能证明已经具备独立 Linux/systemd 24h 或宿主物理断网认证证据**。
本次没有进入其他项目容器、启动服务、复制 Bot 凭据、创建后台 soak 或改变网络。

仍需的真实前置条件与结果：

1. 已明确归属的 Linux/systemd 验收主机、持久状态目录和只监听 loopback 的观测端点，且确认其对应同一服务。
2. 单 Bot 的连接所有权安排；不能保留正式实例连接时另起验收实例抢占连接。
3. 至少 24h 的实际观察窗口、报告及独立实际消息记录；异常/重启恢复另行存档。
4. 主机级断网/恢复操作记录及可达性恢复证据；Docker network detach、fake clock、短 run 都不替代。

定向验证入口：`pnpm exec vitest run scripts/linux-soak.test.ts`。测试使用合成采样和依赖注入时钟，
不连接企业微信、不调用模型、不声明系统级或真实 24h 通过。完整回归入口：`pnpm run ci`。
本分支验证结果：33 项 soak 测试、37 个测试文件共 312 项完整回归，以及格式、类型和公开仓库检查均通过。
